## Осталось прогнать

1. **Собрать iOS.** Правка `bindCurrentDevice()` в `CoreClient.swift` и её
   вызовы в `Session.swift` написаны, но **не компилировались**. Это самое

   (сессия из Keychain переживает удаление приложения, локальный `device_id` —
   нет; см. NEW-1 в отчёте).

2. **Миграция `totp_pending_secret` на копии боевой базы.** Не прогонялась:
   команды, задевающие 2FA, блокировал классификатор auto mode. Проверить,
   что колонка добавляется к существующей таблице `users` и что уже включённая
   2FA продолжает работать (`/2fa/status` = enabled, вход с кодом).

3. **Сырой WS-хендшейк по старому `?token=`.** По той же причине не прогонялся.
   Новый путь `?ticket=` и одноразовость билета проверены (`WS-TICKET-001`).

4. **Таблица веток в отчёте.** `git` был недоступен в обеих сессиях, дат и

## Осталось решить (продуктовые решения, не правки)

1. **RB-1: ротация группового ключа при удалении участника.**
   `remove_group_member` и `leave_group` делают один `DELETE` — ключ K1 живёт
   дальше, удалённый расшифровывает новые сообщения. Сервер ключа не знает,
   значит ротацию делает клиент-админ. Предложенная форма: `groups.key_epoch`,
   `PUT /groups/{id}/key` (атомарно перекладывает `encrypted_key_b64` всем
   оставшимся, отвергается при неполном покрытии), `rekey_required` в ответе
   remove/leave, эпоха внутри группового конверта. Правка сразу в server + web
   + Android + iOS.

2. **RB-2: публичная обычная группа отдаёт ключ серверу.**
   `set_group_public` читает `is_channel` и не использует его. README обещает,
   что сервер знает ключ только у публичных **каналов**. Варианты: требовать
   `is_channel = 1` (сломает уже созданные публичные группы) либо переписать
   README и предупредить в UI.

3. **NEW-3: форма идемпотентности.** Подтверждено: Android при ретрае
   пересобирает конверт (`retryPendingCopies` заново шифрует), поэтому
   отпечаток конверта не совпадёт и честный ретрай получит 409 вместо
   `duplicate: true`. Отпечаток при этом не может поймать то, ради чего
   добавлен: и Ratchet, и AES-GCM недетерминированы, «другой текст» от «тот же
   текст, перешифрованный» он не отличает. Варианты: убрать отпечаток из
   сравнения (оставив `sender` + `recipient` + `recipient_device_id`) либо
   ввести идемпотентный ключ, который клиент считает до шифрования.

4. **NEW-2: чем должен быть пиннинг устройства.** Сейчас это гигиена, не
   граница: `PUT /sessions/me/device` перезаписывает пин безусловно и без
   доказательства, так что держатель токена читает инбокс любого своего
   устройства за один лишний запрос. Ужесточать нельзя без нового
   доказательства владения — публичный `identity_key_b64` им не является.

5. **NEW-5: осиротевшие медиа.** Таблица `uploads` заполняется только новыми
   загрузками; файлы, лежащие на диске с прошлых версий, не считаются в квоту и
   не удаляются TTL-сборщиком. Нужен ли разовый скрипт учёта — решение
   владельца.

6. **NEW-4: `/avatars` не проверяет квоту** (`upload_file` проверяет,
   `upload_avatar` — нет, хотя пишет в ту же таблицу и в ту же сумму). Плюс
   квота проверяется до сохранения, поэтому реальный потолок —
   `UPLOAD_QUOTA_MB` + 50 МБ.

## Коммит

Ветка `android-parity` — не дефолтная, коммитить можно прямо в неё. Перед
`git add -A` стоит знать, что `protocol_vectors/` подтягивается впервые: это
ровно `v1/README.md` и `v1/vectors.json`, и они должны быть в репозитории,
иначе CI их не увидит.

```bash
git add -A
```

```bash
git commit -F - <<'EOF'
Аудит безопасности: закрыть понижение 2FA, подмену device_id, потерю сообщений

P0: POST /2fa/setup снимал включённую 2FA без пароля и текущего кода — угнанная
сессия заменяла второй фактор владельца на свой. Введён totp_pending_secret:
активный фактор живёт до подтверждения замены.

P1: /messages/ack и /messages/inbox доверяли device_id из запроса — сессия
одного устройства подтверждала (и навсегда прятала) сообщения другого. device_id
берётся из сессии; сессия без привязки пиннится к первому значению. Это чинит
случайный путь, но не злонамеренный: PUT /sessions/me/device перезаписывает пин
без доказательства владения, и держатель токена по-прежнему доходит до инбокса
любого своего устройства за один лишний запрос (NEW-2 в отчёте).

P1: target_device_id не проверялся на принадлежность получателю — сообщение
"в никуда" принималось с 200 ok.

P1: повтор client_id сверялся только по отправителю — тот же UUID с другим
получателем или текстом молча выбрасывал сообщение. Сверяется весь неизменяемый
набор плюс отпечаток конверта. Отпечаток спорен: Android при ретрае пересобирает
конверт, поэтому честный ретрай после неоднозначного сбоя получит 409 вместо
duplicate: true (NEW-3, требует решения).

P2: WS-токен уезжал в query-строку (значит в логи прокси) — добавлен одноразовый
POST /ws/ticket, приём ?token= сохранён для установленных сборок; медиа получили
владельца, квоту и TTL-сборщик (по умолчанию выключен) и удаляются при wipe;
проверка существования пользователя при добавлении в группу; проверка формы
публичного ключа аккаунта.

P3: утечка WS-соединений при не-Disconnect исключении; ветка inbox с since
возвращала автору его же групповое сообщение.

iOS: сессия, восстановленная из Keychain или полученная при связывании
устройств, не объявляла своё устройство — login туда не заходит. Keychain
переживает удаление приложения, локальный device_id нет, поэтому после
переустановки старый токен приходил с новым device_id и получал 403 на inbox
навсегда. Добавлен bindCurrentDevice() и вызовы из Session.activate() и
Session.signIn(paired:). Не скомпилировано: сборка iOS была недоступна.

Веб: ensureRatchetKeys() умеет сменить device_id посреди живой сессии, а
привязка делалась один раз после логина — добавлен вызов привязки при смене.

Тесты и CI: server/test_security_regressions.py на всё перечисленное,
core/tests/protocol_vectors.rs (ридер golden-векторов, который README обещал,
но которого не существовало), .github/workflows/ci.yml — до этого в CI была
только сборка iOS и не запускался ни один protocol/security-тест. В job server
не хватало шага, открывающего регистрацию: свежий инстанс стартует в APPROVAL,
и весь job падал бы на 403 approval_required.

Всё перечисленное прогнано на живом сервере с одноразовым PostgreSQL: 54 теста
ядра, 14 golden-векторов, четыре серверных набора, два веб-набора — зелено.
Прогон нашёл дефект в самом регресс-тесте (KEYSHAPE-001 подменял пустой ключ
валидным и потому ничего не проверял) — исправлен; сервер там был прав.

Отчёт: SECURITY_AUDIT_2026-08.md. Не исправлены и требуют решения: ротация
группового ключа при удалении участника, публичная обычная группа отдаёт ключ
серверу вопреки README, форма идемпотентности (NEW-3) и статус пиннинга
устройства (NEW-2).

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
EOF
```
