# P6 — Дизайн: TOFU-пиннинг ключей + «цифры безопасности»

Статус: **реализовано** (см. раздел «Карта реализации» внизу). Сборка успешна.

## 1. Угроза

Сервер (или взломавший его) может подменять ключи в двух местах:

1. **Исходящие**: клиент шифрует на `GET /users/{id}/public-key` — сервер может выдать свой ключ и читать/переписывать всё, что мы отправляем (классический MitM).
2. **Входящие**: `syncInbox` расшифровывает конверт ключом `sender_pubkey_b64` *из самого конверта* и верит полю `sender_id` от сервера. Никакой привязки «sender_id ↔ ключ» нет: сервер может вставить сообщение «от Алисы», зашифрованное любым ключом, и клиент его примет. Это даже шире, чем MitM на чтение, — это спуфинг авторства (усугубляет и P2.7: edit-контрол «от Алисы» может изготовить сервер).

TOFU (trust on first use) не защищает от подмены *до* первого контакта, но превращает «тихий» MitM в **детектируемый**: для подмены после первого контакта серверу придётся менять ключ, что клиент заметит и покажет. Сверка цифр безопасности закрывает и первый контакт.

## 2. Данные (клиент, Room)

Новая таблица `pinned_keys` (Room на `fallbackToDestructiveMigration` — миграция не нужна):

```
PinnedKeyEntity(
  peerId: String,        // PK, lowercase
  publicKeyB64: String,  // запиненный ключ
  pinnedAt: Long,
  verified: Boolean,     // прошла ли ручная сверка цифр
  previousKeyB64: String?, // последний старый ключ (для баннера «ключ сменился»)
  changedAt: Long?
)
```

Свой ключ уже хранится в SecurePrefs — участвует в вычислении цифр.

## 3. Правила (ядро)

Один класс-гейт `KeyTrustStore` поверх DAO, через который идут **все** получения ключей:

**Исходящие** (`getPublicKey` → `KeyTrustStore.keyFor(peerId)`):
- Нет пина → берём с сервера, пиним (TOFU), используем.
- Есть пин, сервер вернул тот же ключ → используем.
- Есть пин, ключ **другой** → отправка блокируется, диалог: «Ключ собеседника изменился. Это смена устройства или атака. Сверьте цифры безопасности». Кнопки: «Сверить», «Принять новый ключ» (перепин, `verified=false`), «Отмена». Никакого тихого перепина.

**Входящие** (`syncInbox`, перед `crypto.decrypt`):
- Нет пина для `m.senderId` → TOFU: пиним `env.sender_pubkey_b64`.
- Пин есть и совпадает → ок.
- Пин есть и **не совпадает** → сообщение не отображается как обычное; в чат кладётся системная плашка «Получено сообщение с неизвестным ключом — возможна подмена», `previousKeyB64`/`changedAt` обновляются, чат помечается ⚠️. (Вариант мягче — показывать текст с красной рамкой — хуже: пользователи игнорируют.)
- Бонус: контролы `edit`/`reaction`/`read` принимаются только при совпадении ключа с пином — закрывает спуфинг контролов сервером.

**Каналы** (`CHANNEL_*`) из схемы исключаются — там сейчас нет шифрования вовсе (отдельная тема).

## 4. Цифры безопасности

Как в Signal: общий отпечаток пары, одинаковый у обоих.

```
fp(user) = SHA-512( "AetherSafety#1" || userId || publicKey )  → первые 30 байт → 30 цифр (по 5 в группе)
safety_number = конкатенация двух fp, отсортированных лексикографически  → 60 цифр, 12 групп по 5
```

- Одинаков у обеих сторон независимо от направления; меняется при смене любого из ключей.
- Версионный префикс — чтобы потом менять формат.
- QR-код (та же строка) — опционально, второй итерацией.

## 5. UI

1. **Экран «Цифры безопасности»** (вход из шапки чата / профиля собеседника): 60 цифр крупно, текст-инструкция «сверьте по другому каналу», кнопка «Отметить как сверенные» → `verified=true`, бейдж ✅ в шапке чата.
2. **Диалог смены ключа** (см. правила выше). Если был `verified=true` — формулировка жёстче, `verified` сбрасывается.
3. **Системные плашки** в ленте чата: «ключ изменился», «сообщение с неизвестным ключом».

## 6. Сервер

Изменений **не требуется** — в этом и смысл: клиент перестаёт доверять серверу. Опционально позже: endpoint прозрачности ключей (журнал смен) — вне скоупа.

Замечание: `PUT /users/me/public-key` позволяет легитимно сменить ключ — после неё все собеседники получат предупреждение. Это ожидаемое поведение.

## 7. Краевые случаи

- **Переустановка приложения у собеседника** (новый ключ при той же регистрации) → предупреждение у всех его контактов. Корректно: это и есть событие, которое надо подтверждать.
- **Свой re-login на новом устройстве**: ключ восстанавливается из `encrypted_private_key_b64` — пин у собеседников не ломается. Если ключа на сервере нет (P3.9) — входа нет, конфликт не возникает.
- **Гонка TOFU**: первый исходящий и первый входящий могут запинить разные ключи при активной атаке — окно неустранимо без сверки цифр; фиксируем «кто первый», расхождение всплывёт предупреждением.
- **Старые чаты при первом апдейте**: всех текущих собеседников пиним лениво при первом обращении (массовый TOFU). Атаку, начавшуюся до апдейта, это не выявит — только сверка цифр.

## 8. Объём работ (оценка)

| Шаг | Файлы | Оценка |
|---|---|---|
| Entity + DAO + KeyTrustStore | data/ | S |
| Гейт исходящих (все `getPublicKey` в MainActivity ~8 мест → один хелпер) | MainActivity | M |
| Гейт входящих + плашки | MainActivity (syncInbox), ChatScreen | M |
| Экран цифр + verified-бейдж | новый Screen, ChatScreen | M |
| Диалог смены ключа | ChatScreen/общий | S |

Итого ~2–3 дня работы с тестированием на двух устройствах. QR-сверка — отдельной итерацией.

## 9. Порядок реализации

1. KeyTrustStore + пиннинг входящих (самое дешёвое и сразу закрывает спуфинг авторства).
2. Гейт исходящих + диалог смены ключа.
3. Экран цифр безопасности + verified.
4. (потом) QR, прозрачность ключей, шифрование каналов.

# Карта реализации (для дальнейших правок)

## Файлы

| Файл | Роль |
|---|---|
| `data/PinnedKeyEntity.kt` | Таблица `pinned_keys` (Room, версия БД поднята до 5) |
| `data/PinnedKeyDao.kt` | DAO — напрямую из UI не использовать |
| `crypto/KeyTrustStore.kt` | **Вся логика доверия здесь.** TOFU, гейты, цифры безопасности |
| `ui/screens/SafetyNumberScreen.kt` | Экран сверки, отметка «сверено», принятие нового ключа |
| `MainActivity.kt` | Интеграция: создание trustStore, `keyFetcher` после логина, гейт входящих в `syncInbox`, маршрут `safety/{peerId}` |
| `ui/screens/ChatScreen.kt` | Кнопка-щит в шапке (параметр `onOpenSafety`) |

## Точки расширения

- **Сменить реакцию на чужой ключ во входящих**: `MainActivity.syncInbox`, блок с `checkIncoming` — сейчас плашка + отклонение; текст и поведение меняются там.
- **Сменить поведение исходящих**: `KeyTrustStore.keyForSending` бросает `KeyChangedException`; её message показывается в чате как ошибка отправки. Хотите диалог вместо текста — ловите этот тип в ChatScreen.
- **Алгоритм цифр**: `KeyTrustStore.safetyNumber` / `fingerprint`; при изменении поднимите `SAFETY_VERSION`.
- **QR-сверка**: добавить в `SafetyNumberScreen` (строка `number` уже есть).
- **Бейдж «сверено» в шапке чата**: читать `trustStore.pinFor(peerId)?.verified` и передавать в ChatScreen (сейчас статус виден только на экране цифр).

## Инварианты (не ломать)

1. Ключи собеседников добываются ТОЛЬКО через `trustStore` (`keyForSending*`), не через `api.getPublicKey` напрямую.
2. Перепин — только явным действием пользователя (`acceptServerKey`). Никаких тихих обновлений пина.
3. Входящие конверты от не-каналов проверяются `checkIncoming` ДО `crypto.decrypt` (конверт расшифровывается ключом из самого себя — без проверки возможен спуфинг).
4. Формат конвертов (`sender_pubkey_b64`/`nonce_b64`/`ciphertext_b64`) не изменён; серверных изменений P6 не требует.
