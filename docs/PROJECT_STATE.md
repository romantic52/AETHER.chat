# AETHER — состояние проекта

Документ для быстрого ввода в курс дела: человека или другой модели. Написан по
факту кода в репозитории на 22.08.2026, а не по памяти. Всё, что здесь названо
готовым, лежит в ветке `web-secure` (она же `main`, они выровнены).

---

## 1. Что это

Самостоятельно размещаемый мессенджер со сквозным шифрованием. Замысел
владельца: официальные серверы — для всех, но любой может арендовать VPS,
скачать сервер, выполнить пару команд и получить ЛИЧНЫЙ сервер для себя и
приглашённых. Собираются только `@username` и пароль — ровно то, что нужно для
уникальности имён и входа. Ни телефонов, ни почты, ни аналитики.

## 2. Из чего состоит

| Часть | Где | Язык | Состояние |
|---|---|---|---|
| Ядро | `core/` | Rust | Готово, общее для клиентов |
| Рэтчет | `core/ratchet-core/` | Rust (vodozemac) | Готово |
| iOS | `ios/` | Swift + SwiftUI | Основной клиент, в активной работе |
| Android | `android/` | Kotlin | Отстаёт от iOS |
| Веб | `web/` | ванильный JS | Работает, близок к паритету |
| Сервер | `server/` | Python + FastAPI | Работает |

Ядро отдаётся в iOS через UniFFI: `cargo build` → `sm_core.swift` +
`SmCoreFFI.xcframework`. Swift-обёртка — актор `CoreClient` (весь ввод-вывод вне
главного потока), поверх него движок `Messaging` (@MainActor).

## 3. Защита

### Переписка один на один
**Double Ratchet (Olm / X3DH)** на крейте `vodozemac` — том же, что в Matrix,
с аудитом Least Authority. Даёт forward secrecy (украли ключ сегодня — вчерашнее
не читается) и восстановление после компрометации. Состояние сессий хранится
pickle-строками в `store.olm_sessions`, аккаунт — в `meta(olm_account)`.
Ключи одноразовые (OTK) выкладываются на сервер, забираются атомарным `claim`;
есть подписанный fallback-ключ и мультисессии. Устаревший `crypto_box` для 1:1
отключён намеренно (`SEC HIGH-1`), даунгрейд невозможен.

### Группы и каналы
Симметричный групповой ключ, розданный участникам через `crypto_box` (X25519 +
XSalsa20-Poly1305). Ротация ключа при изменении состава.

### Медиа
Файл шифруется AES-GCM случайным ключом, ключ едет внутри зашифрованного
сообщения: `{file_id, sym_key, nonce, mime_type, kind}`. Сервер хранит только
шифротекст и ничего о содержимом не знает.

### Ключи на устройстве
Приватный ключ шифруется паролем: PBKDF2 → AES-GCM (`encrypt_private_key`).
База — SQLCipher. Ключ базы в Keychain. Face ID / PIN на вход в приложение.

### Доверие к собеседнику
TOFU (доверие при первом контакте) + сверка ключей вручную: числа безопасности
и QR-код (`olm_verify_qr_build/parse`, `olm_verify_identity`). Смена ключа у
собеседника показывается предупреждением, а не проглатывается.

### Чего защита НЕ даёт
Метаданные видит сервер: кто кому и когда писал, размеры файлов, время в сети.
Это осознанный компромисс — из-за него и предлагается свой сервер.

## 4. Что умеет (iOS)

**Переписка.** Текст, ответы, правка, реакции, пересылка, поиск по чату и
глобальный (люди, группы, каналы), опросы, самоуничтожающиеся сообщения,
закреплённые сообщения, черновиков нет.

**Медиа.** Фото, видео, файлы, голосовые с обрезкой, видео-кружки с записью и
предпросмотром, просмотрщик с зумом, кеш на диске.

**Список чатов.** Закрепление, архив, без звука, удаление; свайпы в обе стороны
с растягиванием крайней кнопки и полным свайпом; папки с умными правилами
(непрочитанные, личные, группы) и ручным списком; ручная перестановка чатов;
предпросмотр переписки по зажатию без отметки о прочтении.

**Группы и каналы.** Создание, роли, профиль группы, публичные каналы с
подпиской и счётчиком просмотров.

**Звонки.** Один на один и групповые (mesh-аудио, сервер только релеит
сигналинг), WebRTC через SPM `stasel/WebRTC`, TURN на своём сервере, Live
Activity звонка в Dynamic Island. Push для входящих звонков заблокирован:
нужен платный Apple Developer.

**Прочее.** Мультиаккаунт с переключением, темы и обои, RU/EN, Face ID / PIN,
очистка кеша, экспериментальный раздел с таймингами свайпа.

## 5. Сервер

FastAPI. Ручки: `/users/register|login|search|{id}/profile|{id}/public-key`,
`/messages` + `/messages/inbox/{id}` + `/messages/ack` + `/messages/views`,
`/groups` (создание, участники, join/leave), `/upload` + `/download/{id}`,
`/avatars`, `/keys/claim/{id}` + `/keys/count`, `/devices/register|unregister`,
`/sessions/me`, `/2fa/*`, `/backup/history`, `/users/me/wipe`, `/health`.
Реальное время — WebSocket `wss://<host>/ws?token=`, ТОЛЬКО HTTP/1.1.

Важно: `/users/register` НЕ возвращает токен — ядро после регистрации делает
login отдельно.

## 6. Как собирать

```bash
cd ios && ./build_core_ios.sh && xcodegen generate
```
`FAST=1` — только симулятор. Затем `xcodebuild`. Клиентские секреты (адрес
сервера, учётка TURN) лежат в `ios/AETHER/Core/Secrets.swift`, он вне git;
шаблон — `ios/Secrets.example.swift`.

**Грабли, стоившие времени:**

- Проект лежит на Desktop, который синхронизируется в iCloud. Из-за этого
  подпись падает с «resource fork, Finder information, or similar detritus not
  allowed», а операции по всей истории git висят часами. Лечение: держать
  derivedData вне синхронизируемой папки; объекты git поднимать с диска
  параллельным чтением (`find .git -type f -print0 | xargs -0 -P 24 -n 4 cat`).
- Clang-модуль в xcframework ОБЯЗАН называться `sm_coreFFI`.
- Симулятора с iOS 27 не существует (Xcode 26.6 даёт 26.5), поэтому баги
  интерфейса на устройстве чинятся только по видеозаписи экрана: кадры тянутся
  скриптом на AVFoundation, дальше сравнивается яркость нужных полос по кадрам.

## 7. Известные слабые места

- **Метаданные** на сервере (см. выше).
- **История git** содержала адрес сервера, пароль TURN и рабочий приватный ключ
  тестового аккаунта; 22.08.2026 история переписана и вычищена, но один
  осиротевший коммит GitHub всё ещё отдаёт по прямому SHA. Ротация на сервере
  отложена владельцем.
- **Пароль TURN в веб-клиенте** публичен по своей природе: браузер скачивает
  скрипт целиком. Правильное решение — временные учётки coturn
  (`use-auth-secret`), пока не сделано.
- **Android** отстаёт от iOS по функциям.
- **Push-уведомления** требуют платного Apple Developer.

## 8. Как здесь принято работать

Фича → сборка на живой iPhone → проверка владельцем → коммит и пуш. Коммиты
описывают не только что сделано, но и почему, с причинами, найденными замерами.
Разработка идёт в `web-secure`, после проверки — ff-merge в `main` и push обеих
веток. Проверять чистоту репозитория надо по ВСЕМ веткам: однажды `main`
отставал на месяц и держал открытыми данные, которые в рабочей ветке уже убрали.
